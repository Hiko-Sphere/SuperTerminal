## SSH authentication and crypto (STSSH)

> **What a writer must not get wrong here.** Five things a marketer must not get wrong here.

1. **Biometrics on Secure Enclave keys is the one unverified piece of an otherwise verified feature.** "Keys generated in the Secure Enclave, accepted by real OpenSSH" is true and tested (STSSHTests/SecureEnclaveKeyTests.swift:24, asserting on sshd's own log). "Requires Face ID before every use" has never been run — the Simulator refuses `.biometryCurrentSet` with LAError -1020, and docs/HUMAN_ACTIONS.md H-7 blocks it. Do not put a Face ID prompt in a screenshot caption or a headline.

2. **There is no built-in authenticator and no local ssh-agent.** 2FA works because the app relays the *server's* keyboard-interactive prompts (verified against a real PAM stack with pam_google_authenticator); the app neither generates nor stores TOTP secrets. Agent support is one-directional: the device answers the server (`ssh-add -l` on the server lists the phone's key — verified), never the reverse. iOS has no system agent to use.

3. **FIDO2 / hardware security keys are refused, and the app says so on its own Keys screen** (App/Sources/Views/KeyManagementView.swift:316). Any copy implying security-key support contradicts the shipping UI.

4. **The algorithm list is shorter than a reader will assume.** Ciphers: aes256-gcm, aes128-gcm, chacha20-poly1305@openssh.com, aes256-ctr — and nothing else. The only MAC offered is hmac-sha2-256-etm@openssh.com; a server narrowed to non-ETM MACs with CTR is unreachable, deliberately. `ssh-rsa` (SHA-1) is refused. Post-quantum mlkem768x25519-sha256 is offered only on iOS 26 and later, and only negotiated where the server supports it. If a comparison table is published, build it from Constants.swift:37-40, SSHConnection.swift:289-298 and SSHKeyExchangeStateMachine.swift:580-637, not from the README.

5. **known_hosts is the app's own JSON file, not OpenSSH's.** There is no import or export of `~/.ssh/known_hosts`, no hashed hostnames, no `@cert-authority` lines. The *policy* (confirm on first use, hard stop on a changed key) is verified against real sshd; the file format is not interoperable, and saying "your known_hosts" would be wrong.

Scope note on evidence quality: almost every "Verified" here rests on a real `/usr/sbin/sshd` spawned by STTestSupport/OpenSSHTestServer.swift (macOS-only fixture) or on stock OpenSSH in a Debian container (Docker-gated — those suites skip silently without Docker, so a green run does not by itself prove keyboard-interactive or password auth ran). The strongest tests assert on sshd's own log lines rather than on the client's self-report, which is the right standard and worth trusting.

## Terminal fidelity — VT/ANSI emulation, colour, graphics protocols, text handling, input, rendering and measured performance (Packages/ApexTerminalKit/Sources/STTerminal, App/Sources/Terminal)

> **What a writer must not get wrong here.** Things a marketer must not get wrong about terminal fidelity:

1. DEC 2026 (synchronised output) and DEC 1004 (focus reporting) are NEGOTIATION ONLY. The modes are parsed, stored and truthfully reported to DECRQM, but nothing consumes them: no code holds a frame back, and no code ever sends CSI I / CSI O. A repo-wide grep for `synchronisedOutput` and `focusReporting` finds hits only inside STTerminal and its own unit test. Never claim tear-free rendering or focus-aware programs. D-062's commit message is carefully worded — "modes the app can act on" — and marketing must be at least as careful.

2. Of the three picture protocols, only SIXEL is verified end to end. It is decoded against ImageMagick-produced bytes, arrives over a real sshd (AppTests/GraphicsSessionTests.swift:64), and is confirmed as actual pixels in the app's own screenshot on two simulated devices (AppUITests/GraphicsUITests.swift:33, recorded at docs/RELEASE_EVIDENCE.md:321). Kitty and iTerm2 inline images are unit-tested only — good tests, including cross-implementation agreement with Pillow's PNG, but nothing sends one from a real server and nothing proves they are drawn. Only sixel belongs in a screenshot or a headline.

3. CJK/Japanese/Korean INPUT is not verified and is explicitly blocked by H-1 (docs/HUMAN_ACTIONS.md:9), which says in terms that until two specific steps are seen on hardware it "must be described" as implemented and unit-tested, not verified. CJK/emoji *display* is a different capability and is verified (real vim over real sshd renders 中文测试, café and 😀). Do not let the two blur into one claim.

4. Throughput numbers are host-Mac numbers. `swift test` runs the emulator benchmarks on macOS; the 16.6 ms render budget runs in the iOS Simulator. No MB/s figure appears in docs/RELEASE_EVIDENCE.md — the 14.7 / 12.7 / 8 MB/s figures exist only as comments in TerminalThroughputTests.swift. What is genuinely enforced on every run are the floors (7 / 15 / 7 MB/s Release, one fifth in Debug). Never attach these numbers to "on iPhone".

5. Themes have zero test coverage of any kind, and "custom themes" is not a shipping feature: AppSettings.customThemes has no editor UI, is never persisted to UserDefaults and is never read at launch — only BackupService writes it on restore, so a restored custom theme vanishes on the next launch. Claim "three built-in themes, light and dark", nothing more. This looks like a genuine defect worth reporting to engineering.

6. Two rendering gaps found by reading the renderer: SGR 5/6 (blinking text) is parsed and stored but never rendered as blinking, and DECSCNM (mode 5, whole-screen reverse video) is tracked in TerminalModes but never applied by TerminalRenderView. The cursor blinks; text does not.

7. SCS / DEC Special Graphics (ESC ( 0) is not implemented — every escape with intermediates is dropped at TerminalEmulator.swift:244. Under a UTF-8 locale this rarely bites, which is why vim/less/htop pass the real-server suites, but "complete VT100 compatibility" would be false.

8. The strongest true claims available, all backed by tests against a real spawned OpenSSH sshd: vim and less draw and restore correctly; a mid-session resize reaches a running full-screen program; 20 000 lines of burst output are consumed within a bounded scrollback; a mouse report reaches the remote program byte-for-byte; OSC 7, 52 and 133 work against a real shell with the real UIPasteboard; changing the font's line height changes what `stty size` reports on the server; a sixel printed by the shell appears as pixels on screen. The parser's "nothing can wedge it" claim is fuzzed with reproducible seeds and was proved capable of failing.

## SFTP and file handling — the in-app file browser, transfers, and the Files.app File Provider extension (audited at HEAD 8434a31; uncommitted work called out separately in notes)

> **What a writer must not get wrong here.** Audited at committed HEAD 8434a31 on branch marketing/app-store-assets.

WHAT IS UNCOMMITTED (do not market, and note it changes one claim above): App/Sources/Services/FileProviderDomains.swift and AppTests/FileProviderDomainTests.swift carry in-flight work referred to as D-073 — the app reads its domains back after publishing and withdraws any the system refused to keep replicated, sets a new user-facing reason string (`notReplicatedNote`), and stops publishing anything else for the rest of that launch. That means: at HEAD, the simulator keeps a downgraded domain and the test asserts the downgrade; with the uncommitted change, the simulator ends up with no domain at all and the Files switch reports itself unavailable. Neither state changes the device story, which remains unverified (H-6). The other uncommitted files (SplitTarget.swift, SplitTargetResolver.swift, ChoosesSplitContent.swift, SplitTargetPicker.swift, SplitTargetTests.swift, SplitWithUITests.swift, plus edits to PaneLayout/SceneState/RootView/TerminalView/AppShortcuts/HostEditorView/ScreenEditorView/Localizable.xcstrings) are a split-pane target picker and are outside this area.

THE THREE THINGS A MARKETER MUST NOT GET WRONG:

1. "Your servers in the Files app" is the single most tempting headline here and it is NOT verified. Every layer under it is proved against a real OpenSSH server — the protocol, the file operations, the enumeration, the identity map, the error mapping, the domain registration, the security refusals — but the only test of the system actually serving those answers (AppTests/FileProviderEndToEndTests.swift) has never run: it disables itself on the simulator and needs a physical device. docs/HUMAN_ACTIONS.md H-6 says in as many words that this "Blocks claiming that servers appear in the Files app." No screenshot of the Files sidebar, no App Store bullet, until H-6 is done and recorded in RELEASE_EVIDENCE.

2. Never say "resumable transfers". Resuming from a byte offset is deliberately refused, in writing, in the code (FileTransfer.swift:96-99). What is true: a running transfer can be paused and resumed; a failed one can be retried and starts over; and a Files-app upload cut by a dead connection recovers by restarting and still lands byte-for-byte with no debris — that last one is genuinely verified against a severed real TCP connection on a real 24 MB upload.

3. "Download to the Files app" (as docs/USER_GUIDE.md:247 currently puts it) is not what the code does. Downloads land in the app's temporary directory; the way out to another app is the share sheet. There is no destination picker.

Smaller things worth not repeating: `signalChange` is dead code, so the app browser and the Files view do not stay in step automatically — a pull-to-refresh is needed. `SFTPSession.move(_:toDirectory:)` is also dead code, so "drag a file from one browser to the other" is not a server-side move and is untested. Drag and drop generally has zero test coverage. The app browser's upload reads the whole file into memory (the File Provider path streams). Transfers stop when iOS suspends the app — there is no background-task handling anywhere in App/Sources.

Safe headline material, all verified against a real OpenSSH server or a real UI run: SFTP over the same SSH connection with no second sign-in; browsing a server's real files with sizes, dates and permission strings; several remote folders open at once, side by side in panes on iPad; and the extension's refusal to trust an unknown or changed host key or to use a Face ID key when nobody is present.

Best screenshot candidates today: the file listing (files-path + file-row), the "Open file browsers" section with two browsers, two browsers in panes on iPad, the permissions editor showing a real mode, and the Transfers screen. Note that AppUITests/MarketingCaptureTests.swift currently captures no file-browser screens at all, so any capture flow for these has to be added.

## Port forwarding and tmux (local/remote/dynamic forwards, inbound channel policy, SSH multiplexing, tmux control mode, session persistence and reattachment, reconnection)

> **What a writer must not get wrong here.** Ground rules a marketer must not get wrong in this area:

1. A forward runs only while the app is running and on screen. iOS suspends a backgrounded app and its sockets stop being served — the app itself says this in the forwards screen (App/Sources/Views/PortForwardsView.swift:49). Never write "always-on tunnel", "background tunnel", "keep your database connected while you work elsewhere".

2. Local and dynamic forwards bind 127.0.0.1 only, deliberately (Packages/ApexTerminalKit/Sources/STForwarding/LocalForwardListener.swift:11-18). Never suggest other devices on the network can use the tunnel, or that the phone becomes a gateway.

3. This is TCP port forwarding, not a VPN. `tunnel@openssh.com` and `x11` are not implemented and are refused by construction (docs/EXECUTION_PLAN.md:73-80). Never write "VPN", "route all your traffic", or "run graphical apps".

4. The SOCKS proxy is CONNECT-only, no authentication, and iOS has no system-wide SOCKS setting — only apps you can point at a proxy can use it. BIND and UDP ASSOCIATE are refused on purpose.

5. "Reconnects automatically after a drop" is true for ordinary terminal sessions and is proven against a proxy that really severs the sockets. It is NOT true for tmux sessions (no reconnection path) and is NOT proven for forwards resuming afterwards. Keep those three claims separate.

6. tmux scrolling is local over ~2000 captured lines, not tmux copy mode. Do not say "full tmux scrollback" or "search your tmux history".

7. Multiplexing is the strongest verified claim in this area: four sessions cost one handshake, counted in the real sshd's own log (Packages/ApexTerminalKit/Tests/STSSHTests/ConnectionPoolTests.swift:29-53). "One connection, one authentication, one Face ID prompt" is safe.

8. Everything marked Verified here was proven on a macOS test host against a real sshd (spawned) or a real tmux (Docker), driving the shipping code — not on an iPhone. The UI-level proofs (PortForwardUITests, TmuxUITests) ran in the iOS Simulator against those same real servers. Nothing in this area is blocked in docs/HUMAN_ACTIONS.md.

9. tmux version measured is 3.3a only (Debian bookworm image, Packages/ApexTerminalKit/Sources/STTestSupport/TmuxTestServer.swift:95-110). Do not claim compatibility with tmux in general or name other versions.

10. For screenshots, only these are backed by Verified capabilities: the port-forwards list with a running rule and its counters, the forward editor showing that a SOCKS rule asks for no destination, a tmux window with two panes after a split, and the tmux toolbar menu. A detached-tmux screen or anything implying background operation should not be used.

## VNC / remote screens (encodings, authentication, routes, input, clipboard, performance)

> **What a writer must not get wrong here.** Do not say "works with macOS Screen Sharing" or "supports VeNCrypt". Both are implemented and well-tested against vectors and a second implementation of the server half, but docs/HUMAN_ACTIONS.md:67 (H-3) names them explicitly as the thing this blocks: "Claiming macOS account login and VeNCrypt work. They are implemented, not verified." No real Mac and no real VeNCrypt server has ever answered this client. The safe wording is "built for macOS Screen Sharing and VeNCrypt sign-in", or nothing.

Do not say "VeNCrypt support" without the exclusion: VeNCrypt's own TLS and x509 sub-types are deliberately not implemented and the connection is closed with an explanation (VNCClient.swift:387). The intended encrypted path is SSH or Cloudflare.

Every "Verified" item in this area rests on ONE server implementation: LibVNCServer from Homebrew, serving a 320x200 pattern on loopback (Packages/ApexTerminalKit/Sources/STTestSupport/Fixtures/vnc-test-server.c). RealVNC, TightVNC, TigerVNC, x11vnc as actually deployed, and macOS have never been connected to. "Works with any VNC server" is not supportable.

Only RFB 3.8 is exercised. The 3.3 and 3.7 code paths (VNCClient.swift:198-203, :361) have no test at all — do not claim "RFB 3.3/3.7/3.8" as verified.

Tight and JPEG encodings — what many people associate with "fast VNC" — are not implemented. Claim ZRLE/Hextile/RRE/Raw/CopyRect, nothing more.

The Cloudflare-tunnelled screen route has never been connected (H-4, needs the owner's Cloudflare account). Screens over SSH are the route that is genuinely proven end to end.

Two privacy/design claims that read well and have NO test: "a remote desktop cannot write your clipboard" (the ServerCutText -> banner path is never exercised by anything) and "the screen is never stored". Both appear true by inspection; neither may be a headline claim.

Performance: quote no fps numbers. The D-030 figures (Raw 4131 fps, ZRLE 800, Hextile 4107) are release-build measurements on a developer Mac against synthetic frames. Nothing has been measured on an iPhone or iPad, and no end-to-end latency or frame rate over a real network exists. The honest claim is "decoding is not the bottleneck", backed by tests that fail if it becomes one.

Screenshot-safe surfaces: the connected screen (vnc-screen, whose accessibility value the UI test pins to "ApexTerminal test desktop, 320 × 200"), the key row with a latched modifier, the screen's own editor, and the screens section of the connection list. A screenshot showing a real macOS desktop or a real Linux desktop would be showing something no test has ever produced.

Terminology: the product calls these "screens" / "remote screens", not "VNC sessions"; the editor is "Edit Screen".

## iPad and multi-platform experience: split panes, multiple sessions, tabs, multi-window, iPad multitasking, hardware keyboard and shortcuts, trackpad/pointer, Mac Catalyst, visionOS, watchOS, shipped platforms

> **What a writer must not get wrong here.** Things a marketer must not get wrong about this area:

1. DO NOT SAY "TABS". There is no tab bar anywhere in this app. Open sessions, screens and file browsers are rows in the sidebar list; you move between them by tapping, by ⌘1–⌘9, or by ⌘⇧[ / ⌘⇧]. `AppUITests/FileBrowserTabsUITests.swift` is misleadingly named — it asserts list rows, not tabs. A reviewer who reads "tabs" and looks for a tab strip will file it as a missing feature.

2. The only iPad claims that survive a strict audit are: split panes with a draggable divider (real, tested against a real sshd on both an iPhone 17 Pro and an iPad Pro 13-inch M5), each pane having its own toolbar on iPad, multiple live SSH sessions with typing following the session on screen, and a genuine second window via "Open in New Window". Those four are the only ones fit for a screenshot or a headline.

3. iPad Split View, Slide Over and Stage Manager are DECLARED (UIRequiresFullScreen = NO, size-class-driven layout) and have NEVER been observed in a test. The whole UI suite runs full-screen. "Works with Stage Manager" would be an untested claim.

4. Mac: the true sentence is "it builds, launches, and its logic passes there" — 316 of 324 unit tests on a Mac. H-8 (docs/HUMAN_ACTIONS.md:219-260) says in as many words that **nothing about how the app behaves on a Mac is verified**, because the UI suite cannot load without a Catalyst signing identity. Also, DECISIONS.md:1407 summarises D-070 as "Catalyst with a real menu bar" and that is not backed by the code — the only `Commands` body is one `CommandGroup(replacing: .appSettings)` at App/Sources/Views/RootView.swift:567-572, and there is no `buildMenu`/`UIMenuBuilder` in the repository. Do not promise a Mac menu bar. Do not promise Files.app/Finder integration on the Mac — it is genuinely absent there and the app says so.

5. visionOS: the app has never been executed there, not once. The project cannot even name a visionOS build destination today. The only permitted phrasing is Apple's own: available on Apple Vision Pro as a compatible iPad app. watchOS does not exist and was deliberately refused.

6. The hardware-keyboard story is stronger than most apps' but narrower than it looks: only ⌘K, ⌘N, ⌘/, ⌘,, ⌘F and the arrow keys have ever been sent as real keys by a test. The split-pane and session-switching shortcuts (⌘D, ⌥⌘W, ⌥⌘[ / ⌥⌘], ⌘1–⌘9, ⌘⇧[ / ⌘⇧], ⌘W) are unit-tested for correctness of the table and the routing, but no test has ever pressed them. Escape and Return into a focused field are known NOT to be deliverable by the simulator instrument and remain unverified.

7. Trackpad and mouse support is real code with real configuration tests, but no test moves a pointer. "Full trackpad support" is a device claim nobody here has made.

8. ACTIVE DIRTY TREE: the "Split With…" feature (a picker for putting a *different* server, screen, folder or brand-new connection in the other half of a split) is entirely untracked in git as of this audit — six files, referencing a "D-074" that does not exist in DECISIONS.md and has no RELEASE_EVIDENCE entry. It is another session's work in flight. Exclude it from every claim, screenshot and release note until it lands.

9. There is no Marketing capture state for split panes. AppUITests/MarketingCaptureTests.swift captures host-key, terminal, sessions, keys, vim, htop, palette, find and editor — the split-pane screenshot that would sell the iPad story does not exist yet and would need a new capture state.

## Cloudflare Access / Cloudflare Tunnel support (STCloudflare, and its app-layer surfaces)

> **What a writer must not get wrong here.** THE ANSWER TO THE HEADLINE QUESTION: no. No connection has ever been made through a live Cloudflare account. Every passing Cloudflare test in this repository runs against `WebSocketCarrierTestServer`, a local NIO server written in this project to reproduce the edge's wire behaviour, bridged to a real local OpenSSH sshd. The one suite that would touch Cloudflare — LiveCloudflareE2ETests — is gated at line 24 on `ST_LIVE_CF_HOSTNAME` and skips. I ran it on 2026-09-10 and watched all four cases report "skipped". docs/HUMAN_ACTIONS.md:81 (H-4) still lists the live environment as blocked on the owner and names what it blocks: "the app's central product claim being *verified* rather than implemented". Even the no-account workaround failed — TEST_REPORT.md:1033 records two `trycloudflare.com` quick tunnels that registered with Cloudflare but returned empty 404s from the edge, with no request reaching the tunnel (PROJECT_STATUS.md:244, B-3).

CONSEQUENCE FOR COPY: no headline, screenshot caption, or App Store claim may assert that Apex Terminal connects through Cloudflare Access, that Access sign-in works, or that a Cloudflare-tunnelled server has been reached. The honest maximal claim is about the client side: the app implements Cloudflare's carrier protocol natively and runs a full interactive SSH session over it with no helper binary — proven against a real sshd, not against Cloudflare.

"NO CLOUDFLARED NEEDED ON THE DEVICE" IS THE ONE STRONG CLAIM, and it is architecturally true rather than merely asserted. Three independent things establish it: STCloudflare reimplements the protocol in Swift over SwiftNIO (CloudflareCarrierTransport.swift:100-166); App/ApexTerminal.entitlements declares no Network Extension and no VPN (its own comment at lines 5-15 says the tunnel is "an ordinary outbound TLS connection made in-process"); and no subprocess-spawning API appears anywhere in App/Sources, FileProvider/ or the shipping package sources — only in test-only STTestSupport servers. What *proves* it operationally is CarrierIntegrationTests.swift:65 and :94: a complete SSH session and a 256 KiB PTY burst run entirely in-process over the app's own carrier. Nothing links or ships cloudflared for those to pass. The protocol itself was derived by reading cloudflared's source at a pinned commit (DECISIONS.md D-001), which is honest engineering but is not the same as observing the real edge.

THREE PROJECT DOCUMENTS OVERSTATE COVERAGE — do not quote them. (1) docs/RELEASE_EVIDENCE.md:1042 says "The probe itself is `AccessDiscovery`, which has its own [tests]"; docs/CLOUDFLARE.md:293 repeats it. There is no AccessDiscovery test file. (2) AccessLogin.swift:5-6 says "tests supply a driver that performs the browser half of the exchange programmatically". There is no such driver — grep finds exactly one implementation of the presenter protocol, the real ASWebAuthenticationSession one. (3) CarrierIntegrationTests.swift:200-201 defers validation coverage to "AccessValidationTests", a suite that does not exist. The STCloudflareTests target contains three files totalling 545 lines, one of which is a four-line base64 round-trip.

WHERE THE UNTESTED MASS IS: of the 1 769 lines in STCloudflare, the carrier (CloudflareCarrierTransport + WebSocketByteStream, ~548 lines) is well covered; the entire authentication half — AccessDiscovery, JWKS/JWSVerifier, AccessTokenValidator, AccessLogin, BoxCrypto, HTTPTransport, ~950 lines — has no test whatsoever. That includes the RS256 pin, the kid-must-match rule, the audience check that prevents token confusion between Access applications, and the crypto_box decryption of the login transfer. The security reasoning in those files is careful and the type system enforces "validated or not at all" (ValidatedAccessToken's initialiser is internal), but careful is not verified.

## Security and privacy posture (key storage, Secure Enclave, biometrics, app lock, host key trust, clipboard/paste, App Switcher shield, what leaves the device, telemetry, accounts, monetization)

> **What a writer must not get wrong here.** Things a marketer must not get wrong about this area.

1. THE FOUR CLAIMS SAFE FOR A HEADLINE OR A SCREENSHOT, and nothing else in this area:
   (a) Secure Enclave SSH keys, device-unlocked policy — logged into a real sshd, confirmed by sshd's own log line and by ssh-keygen; (b) the app lock passcode — unit-tested against the real Keychain and driven end to end through a relaunch by a passing UI test; (c) host key trust on first use and the hard stop on a changed key — proven against two real OpenSSH servers; (d) OSC 52: a program on the server cannot write your clipboard unless you allow it and can never read it — proven against a real sshd with the real pasteboard. Host certificates (e) are equally well proven if you want a fifth.

2. NEVER SAY THE APP BLOCKS SCREENSHOTS OR SCREEN RECORDING. It does not. There is no isCaptured observer, no screen-capture detection, no secure-display flag anywhere in the app. What exists is a cover over the window while the scene is inactive, so the App Switcher snapshot shows the logo (App/Sources/Views/PrivacyShield.swift). On by default, switchable, and untested. Phrase it as "hides your terminal in the App Switcher".

3. NEVER CLAIM FACE ID / TOUCH ID HAS BEEN VERIFIED, anywhere in this app. Three separate biometric surfaces exist — a Secure Enclave key gated per signature, a Keychain key gated per read, and the app lock's own biometric unlock — and NOT ONE of them has ever run against real biometrics in this project. The Simulator has a Secure Enclave but no biometrics, and LocalAuthentication returns Code=-1020 "This call is not supported on iOS Simulator". docs/HUMAN_ACTIONS.md H-7 is the open item and it is explicitly not marked done. Do not stage a Face ID prompt in a screenshot. "Can be protected with Face ID or Touch ID" is fair; "Face ID-protected keys, proven" is not.

4. THE ONE CRACK IN "NOTHING LEAVES YOUR DEVICE". Everything in this build genuinely stays local — iCloud sync is hard-disabled (SyncAvailability.isAvailable = false), which also makes the per-key "Store private key in iCloud Keychain" toggle unreachable, so even the iCloud Keychain path is dead code today. But the OPTIONAL AI assistant, if the user configures a provider endpoint and stores an API key, sends up to 6,000 characters of terminal text plus the last command to that endpoint. It prefers Apple's on-device model and does nothing without a key. Any absolute privacy sentence must be written so it survives that: e.g. "Apex Terminal has no server of its own. Your data goes only where you send it." Avoid unqualified "your terminal never leaves your device".

5. "NO ACCOUNT, NO ANALYTICS, NO SUBSCRIPTION" IS TRUE AND UNUSUALLY WELL SUPPORTED. There is no sign-up flow, no first-party domain anywhere in the source, no analytics or crash-reporting SDK (the dependency list is Apple's swift-nio/swift-crypto family, libsodium via swift-sodium, and a vendored swift-nio-ssh fork — nothing else), an empty NSPrivacyCollectedDataTypes with tracking false in PrivacyInfo.xcprivacy, and ZERO StoreKit/IAP/subscription symbols in the entire tree. Note that this rests on reading the manifests and grepping, not on a test — absence cannot have a test — but it is checkable in seconds by anyone.

6. DO NOT NAME A KEYCHAIN CONSTANT IN A HEADLINE. The code sets kSecAttrAccessibleWhenUnlockedThisDeviceOnly for keys, passwords, service tokens and the app-lock record, and afterFirstUnlockThisDeviceOnly for Cloudflare Access tokens, and it delete-then-adds so a class can never be silently downgraded (KeychainSecureStore.swift:55-60). Real Keychain round trips are tested. But no test reads kSecAttrAccessible back, so the specific attribute is a code-reading claim. Say "kept in the iOS Keychain"; leave the constants to the security page.

7. IOS AND IPADOS ONLY. Every verified claim here was measured on iOS/iPadOS. On Mac Catalyst eight tests including the app lock's fail for want of a signing profile, the UI suite will not even load, and per-file data protection falls back to a plain atomic write (docs/HUMAN_ACTIONS.md H-8). visionOS has never been run at all (H-9). No security claim may be extended to the Mac or to Vision Pro.

8. TRUST ON FIRST USE IS HONEST, NOT MAGIC. The product's own consent screen says the app cannot tell a real server from an impostor on a first connection and asks the user to compare the fingerprint. Marketing should say the same thing — the strength of the story is the CHANGED-key refusal, which is what most mobile SSH clients get wrong and which this project proves against two real servers.

9. Two smaller ones stated precisely: clipboard expiry is set via UIPasteboard's expirationDate and defaults to 60 seconds, but no test watches it expire — say "set to expire", not "proven to vanish". Multi-line paste confirmation is exhaustively unit-tested as a decision function, but no test sees the sheet appear in front of a live shell.
